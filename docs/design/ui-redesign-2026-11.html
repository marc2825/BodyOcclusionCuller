UnderWhere UI再設計案

現在のサイドバー（v1.1.2）の課題を24点に整理し、作り直しの方向を3つ示します。実装はまだ行っていません。どの案で進めるかを選ぶための資料です。

現在のUIの課題

コード（ui.py のパネル描画）、ティザー画像、自動テストのスクリーンショットをもとに洗い出しました。重要度は、使い始めの人が作業を完了できるかどうかへの影響で付けています。右のモックの番号は、表の番号に対応します。

#重要度課題根拠
構造
1高縦に長く、主な操作が離れている番号付きパネル5つとサブパネル4つが1列に並びます。Analyzeは中ほど、出力は一番下で、解析後はスクロールが必要です。
2中今どの段階にいるかが示されない番号は順序を示しますが、全パネルが同時に開いたままで、次に押すものが強調されません。
3低番号の体系が二重になっているパネルの「1〜5」の中に「1 Choose faces」「2 Change them」があります。
4高状態表示が内部用語の1行READY、CHECK: inputs updated; verified on next operation、MODIFIER_UNSUPPORTED: … など。状態・進捗・直前のエラーが同じ行に入り、幅が狭いと途切れます。
5中結果パネルに要約・警告・診断・操作が混ざる警告はすべて同じアイコンです。「共有頂点のため残る」のような情報も、エラーと同じ見た目です。

言葉
7高言語が混ざっているボタンは英語、判定の理由はBlenderが日本語のときだけ日本語です。英語環境では、内部コードを整形しただけの文になります。
8高内部用語・専門用語が多いOccluders、Preflight、Work budget、States、Audit、Assume opaque、View Ray。文書では「衣装」、画面では「Occluders」と呼び方も違います。
9中同じ語に複数の意味があるKeep は判定の名前でもあり手動操作でもあります。Hide は候補・操作・出力の3か所で使われます。
10中出力ボタンの違いが名前から分からないApply to New Copy と Create Deleted Copy (FBX)。どちらを選ぶべきかは文書を読まないと分かりません。
操作
11中最初の選択肢が多いモード2つ、検査範囲2つ、処理量4つ、PreflightとAnalyzeが、同じ重みで並びます。
12中入力の決まりが見えないUse Selection は「Bodyを最後に選ぶ」前提です。＋ボタンの動きもリストごとに違います（衣装は空欄を追加、Bodyパーツは選択中のメッシュを追加）。
13高確認する場所が実物から離れている横に置いた比較メッシュの上で確認します。色を見るにはMaterial Previewへの切り替えが必要で、衣装を着た実物の上では見られません。Edit Modeへの切り替えも伴います。
14中安全のための仕組みが見えにくいOnly change Review faces は既定でオンで、対象外の面を黙って外します。Hide は毎回確認ダイアログが出ます。
15中進み具合と終わりが見えない未判定の面があといくつ残っているか、確認が済んだかどうかを示す表示がありません。
16高再解析で手動の指定が消える結果はファイルに保存されず、開き直すと再解析が必要です。そのとき Keep / Hide の指定は引き継がれません。
17低出力したあとの案内がないコピーは元のBodyと重なって作られます。どれを書き出すかは文書頼みです。
見た目
18中強弱が弱く、説明文が常に場所を取るほぼすべての行がアイコン付きのラベルです。操作のヒントが常設で、縦の長さを増やしています。
19中色の意味が表示モードで変わる緑は Classification で「隠す候補」、Before / After で「新たに隠れる」、Poses で「全フレームで隠れる」。色相だけで区別しているため、色覚によっては緑・黄・橙・赤が見分けにくくなります。
20低凡例の色見本が実際の色と少し違うBlenderの既定アイコンを流用しています。白は枠だけのアイコンです。
21中幅が狭いとラベルが途切れる自動テストのスクリーンショットで「Update Com…」「Mask hide…」と表示されています。
22中数字に文脈がない件数だけで割合がありません。Candidate と Output hides の差は、離れた警告行で説明されます。
知らせ方
23低成功の知らせがすぐ消える画面下のステータスバーに一時的に出るだけです。
24低初めて開いたときの案内がない最初の表示は「Choose Body and occluders」の1行と、全部の操作部品です。

今のままでよい点

  • 元のBodyを変更しないこと、判断できない面を自動で隠さないことが、画面の作りにも一貫して表れています。
  • ほぼすべての部品にツールチップがあります。
  • 結果が古くなったときに、理由と再解析のボタンが出ます。
  • 全パネルの描画が自動テストで確かめられています。作り直しても同じ方法で検証できます。

作り直しの前提

Blenderのサイドバーは、フォント・色・余白をアドオン側から変えられません。変えられるのは、構成、文言、アイコン、進捗バー、ポップオーバー、そして3Dビューポートへの直接の描画です。そのため「洗練」は、部品の装飾ではなく、情報の順序と量、言葉、ビューポートの使い方で行います。

どの案でも行うこと

  • 画面の言葉を日本語と英語の両方で用意し、Blenderの言語設定に合わせます（課題7）。
  • 用語を下の表のように言い換え、1つの語に1つの意味だけを持たせます（課題8、9、10）。
  • 状態表示を「今どうなっていて、次に何をするか」の文にします。エラーは起きたことと直し方を書きます（課題4）。
  • 解析が終わったら、色分けを自動で表示します（課題6）。
  • 面の構成が変わっていなければ、再解析のあとも手動の指定を引き継ぎます（課題16）。
  • 知らせを「情報」「注意」「エラー」の3段階に分けます（課題5）。
  • 件数に割合を添えます（課題22）。

案A　ステップ式

サイドバーに、今の段階の内容だけを表示します。段階は「準備」「確認」「書き出し」の3つで、上の切り替えでいつでも戻れます。各段階で一番目立つボタンは1つだけです。

解決する課題
1、2、3、11、15、18、21。スクロールがほぼなくなり、次に押すものが常に分かります。
良い点
初めての人が迷いません。解析や出力のコードは変えないので、不具合が入りにくい作り直しです。
弱い点
慣れた人には、段階の切り替えが手数になります。確認は今と同じく横の比較メッシュの上で行うので、課題13は残ります。
実装の規模
中。ui.py のパネル構成の作り直しと、パネル描画テストの更新です。

案B　ビューポート主役

確認の作業を、サイドバーではなく3Dビューポートで行います。横に比較メッシュを置く代わりに、素体そのものに判定の色を重ねます。専用のツールで、なぞった面を「隠す」「残す」に直接塗り分けます。Edit Modeへの切り替えは要りません。

解決する課題
1、13、14、15、18、19、20。課題13（実物の上で確認できない）を解決できるのはこの案だけです。色見本や縞模様も自前で描けるので、色覚への配慮も入れられます。
良い点
見たままを直接触る操作になります。視線がサイドバーとビューポートを往復しません。
弱い点
画面への描画、専用ツール、面の当たり判定を新しく作る必要があります。自動テストで確かめにくい部分が増え、Blenderのバージョンの違いにも影響されやすくなります。
実装の規模
大。色を重ねる表示だけなら中、塗り分けツールまで含めると大です。

案C　やることリスト

段階に分けず、1枚のパネルにまとめます。解析の結果から「次にやること」を自動で作り、削減できる面数への影響が大きい順に、対処のボタンと一緒に並べます。すでにある診断（理由の内訳、素材、大きさ）を、読む順序に並べ替える案です。

解決する課題
1、5、11、15、18、22。「候補が少ないのはなぜか」に、画面が先回りして答えます。
良い点
慣れた人には最短です。3案のうち実装が一番小さく済みます。
弱い点
初めての人には、全体の流れが案Aほどはっきりしません。課題13は残ります。
実装の規模
小から中。

おすすめは、案Aを骨組みにして段階的に進めること

3つの案は組み合わせられます。次の順で進めると、早い段階で効果が出て、危険の大きい部分を後回しにできます。

  • 第1段階：「どの案でも行うこと」と案Aの3段階の構成。案Cの「次にやること」を、案Aの「確認」の段に入れます。
  • 第2段階：案Bのうち、素体に色を直接重ねる表示だけを追加します。面の選択は今の仕組みのまま使います。
  • 第3段階：使われ方を見てから、案Bの塗り分けツールを作るかどうかを決めます。
